# iSmartCar 🚗

**iSmartCar** — модернизация радиоуправляемой машинки **SunFounder Smart Video Car Kit** на базе **Raspberry Pi 3B+**.

**Цель:** сохранить штатные моторы, сервоприводы, платы управления и USB-камеру, но обновить проект до **Python 3.12**, добавить **Bluetooth-геймпад**, передавать видео по **Wi-Fi на Android-смартфон** и перейти на питание от **одного повербанка**.

> 🚧 **Статус (25.10.2026): активная разработка и стендовые испытания.** G910 подключается через ASUS USB-BT400 и автоматически переподключается после выключения/повторного включения; все оси и кнопки проверены через `evdev`. Программная логика PWM прошла 11 unit-тестов, но физический привод моторов/сервоприводов **не испытан**: контроллер PCA9685 сейчас не отвечает по I²C (`0x40` отсутствует).

## Возможности (план)

- Управление движением, рулём и поворотом камеры с беспроводного Bluetooth-геймпада.
- Штатная USB-камера остаётся на машинке.
- Android-смартфон используется **только как видеомонитор** через браузер.
- Локальная работа без интернета: Raspberry Pi и смартфон соединяются по Wi-Fi.
- Один повербанк питает машинку через правильно подобранные преобразователи.
- Безопасность: остановка двигателей при потере Bluetooth-соединения или сбое.
- Автоматический запуск программы после включения Raspberry Pi.

### ⚠️ Особенности питания

Обычный выход повербанка на 5 В **нельзя без проверки подключать вместо штатного блока аккумуляторов**, если исходное питание двигателей и преобразователей рассчитано на другое напряжение.

Перед подключением определим характеристики повербанка, двигателей, сервоприводов и DC-DC-преобразователей. Raspberry Pi, сервоприводы и моторы получат соответствующие линии питания с необходимым запасом по току. Питание моторов **не должно проходить через Raspberry Pi**; для цепей управления обеспечим корректную общую землю.

Точную электрическую схему опубликуем после измерений и проверки железа.

## Видео на Android

```text
USB-камера → Raspberry Pi → Wi-Fi → браузер Android-смартфона
```

Используем локальный видеосервер (например, MJPEG-streamer или совместимую альтернативу). Wi-Fi-сеть может предоставлять домашний роутер или точка доступа смартфона. Интернет не обязателен.

Начнём испытания с 640×480 и 15–20 кадров/с, затем оценим задержку. Bluetooth и Wi-Fi Raspberry Pi 3B+ используют диапазон 2,4 ГГц, поэтому совместную работу надо проверить.

## Фактически проверено на Raspberry Pi 3B+ (24.10.2026)

- Debian Bookworm aarch64, Python 3.11.2; консольный режим `multi-user.target`.
- I²C `/dev/i2c-1`; PCA9685 отвечает на `0x40` (также виден `0x70` All Call), регистры: MODE1=`0x11`, MODE2=`0x04`, PRESCALE=`0x1E`.
- Logitech C270 определяется через USB; HTTPS Flask-видеосервер на порту 9095 проверен отдельно.
- G910 сопряжён через ASUS USB-BT400 (BCM20702A0), события устройства `Gamepad` получены через `evdev`.
- Оси: `ABS_X` — руль, `ABS_Y` — тяга, `ABS_Z` — панорама камеры, `ABS_RZ` — наклон; все оси проверены от −100 до +100% в dry-run.
- Кнопки: A — центр руля, B — аварийная остановка, X — центр камеры, Y — уровень скорости (в **симуляции**).
- В `src/ismartcar/hardware/actuator_mapping.py` реализован чистый пересчёт процентов в целевые значения для **штатных** каналов CH0, CH4, CH5, CH14, CH15 при 60 Гц. Это **расчёт, не управление железом**. Для камеры поставлены пробные ограниченные диапазоны, физическая калибровка не выполнена.
- Проблема питания `vcgencmd get_throttled = 0x50005` не устранена. **Подача команд PWM/движение моторов пока не испытывались.**

### Первое испытание тяговых двигателей G910 (только с поднятыми колёсами)

`src/ismartcar/controllers/g910_motor_test.py` повторяет направление из оригинального
`Sunfounder_Smart_Video_Car_Kit_for_RaspberryPi/server/motor.py`:
GPIO.BOARD 11/12 — Motor0, 13/15 — Motor1; PWM PCA9685 CH4/CH5, 60 Гц.
Отдельно проверены `forward0 = True`, `forward1 = True` в оригинальном `server/config`.

- По умолчанию программа показывает описание, **не включает** GPIO/PWM.

### Автоматическое подключение MOBASE G910 через ASUS USB-BT400

После первичного сопряжения (уже сделано на этой Raspberry Pi) процесс
`src/ismartcar/controllers/bluetooth_autoconnect.py` использует BlueZ D-Bus
`org.bluez.Device1.Connect`. Он находит **именно USB-BT400** по адресу
`5C:F3:70:7F:E0:D4` (встроенный Bluetooth Raspberry Pi не выбирает)
и переподключает **G910** `05:67:39:43:89:01` при загрузке и после обрыва.
Он не включает двигатели, PWM, I2C или GPIO. При выключенном геймпаде
периодически повторяет попытки; включить сам геймпад физически не умеет.

```bash
cd /home/pi/iSmartCar
git pull --ff-only
sudo apt install -y python3-dbus
sudo /usr/bin/python3 src/ismartcar/controllers/bluetooth_autoconnect.py --once
# Если геймпад уже подключён и первая проверка прошла успешно:
sudo cp systemd/ismartcar-gamepad.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now ismartcar-gamepad.service
systemctl status ismartcar-gamepad.service --no-pager
journalctl -u ismartcar-gamepad.service -n 30 --no-pager
```

Не требуется заново выполнять `pair`, если G910 остался сопряжён с
ASUS-адаптером. При ошибке `Powered` проверьте `rfkill list`, при
необходимости разблокируйте адаптер командой `sudo rfkill unblock bluetooth`.
Для диагностики после включения геймпада можно выполнить
`bluetoothctl info 05:67:39:43:89:01` или
`sudo python3 src/ismartcar/controllers/gamepad_probe.py --list`.
Для отключения службы:
`sudo systemctl disable --now ismartcar-gamepad.service`.

аналоговые, события. `EV_KEY=2` — автоповтор удерживаемой кнопки

```bash

```

Dry-run показывает события, не обращаясь к GPIO/I²C и не двигая машину.

### Переподключение G910 после автоматического выключения

Обновлённый `bluetooth_autoconnect.py` не только пытается подключиться к
уже сопряжённому G910 через `Device1.Connect`, но и после нескольких
ошибок запускает **короткий BR/EDR-поиск (7 секунд)** именно на ASUS USB-BT400.
При отсутствии записи об устройстве поиск выполняется с интервалом не чаще
40 секунд. Используется постоянное соединение с системной шиной D-Bus,
чтобы BlueZ не прерывал сеанс поиска при закрытии клиента.
Автоподключение **не** стирает сопряжение и **не** включает моторы.

Для применения обновлений **уже установленной** службы:

```bash
cd /home/pi/iSmartCar
git pull --ff-only
python3 -m py_compile src/ismartcar/controllers/bluetooth_autoconnect.py
sudo systemctl restart ismartcar-gamepad.service
systemctl status ismartcar-gamepad.service --no-pager
sudo journalctl -u ismartcar-gamepad.service -f
```

Контроллер G910 **полностью выключается** после бездействия, а не уходит в сон.
После повторного включения HOME он должен снова подключаться к ASUS.
**Проверено 25.10.2026:** вначале соединение по BlueZ формально было
`Connected: yes`, но отсутствовали события HID; после ручного `disconnect`
и `connect` соединение восстановилось. Затем обнаружили, что для диагностики
была **остановлена systemd-служба**. После `sudo systemctl restart ismartcar-gamepad.service`
пользователь подтвердил автоматическое подключение при повторном включении G910.
Для обычной работы служба должна оставаться **active (running)**.
Контролируем журнал командой `sudo journalctl -u ismartcar-gamepad.service -f`.
Не следует принудительно отключать соединение только на основании отсутствия
событий стиков: отсутствие событий в покое — нормальное поведение.
Если после 30–60 секунд реального включения он не соединяется,
сохранить журнал для диагностики ошибок BlueZ и состояния `ReconnectMode`
HID. Не применять `remove`/повторное `pair` до чтения журнала.
Скрипт не может физически разбудить выключенный контроллер;
он пробует подключиться, когда тот снова доступен в эфире.

### Текущее состояние электроники и питания (25.10.2026)

- Проверено: `/dev/i2c-1` существует; `i2c_dev`, `i2c_bcm2835` загружены,
  в `/boot/firmware/config.txt` включено `dtparam=i2c_arm=on`.
  `pinctrl get 2` показывает SDA1, `pinctrl get 3` — SCL1.
- **Блокер:** `sudo i2cdetect -y 1` сейчас не показывает
  PCA9685 ни по `0x40`, ни по `0x70`.
  Когда плата отвечала раньше, `MODE1=0x11`, `MODE2=0x04`,
  `PRE_SCALE=0x1E`; CH0, CH4, CH5, CH14, CH15 были FULL_OFF.
- Во время запуска `g910_motor_test.py --arm` чтение PCA9685 закончилось
  `OSError: [Errno 121] Remote I/O error`, **моторы не запускались**.
  Программа затем была изменена: сначала проверяет I²C, потом настраивает GPIO,
  и не обещает успешное аппаратное выключение PWM, если шина не отвечает.
- От внешнего Mean Well RS-15-5 Raspberry Pi загружалась,
  но при иной схеме питания фиксировались периодические `0x50005`
  (текущее низкое напряжение/троттлинг) и `0xD0008`
  (температурный предел). `0x50000` и `0xD0000` —
  исторические события, при отсутствии младших битов текущей ошибки нет.
- Два аккумулятора 18650 показывали 1,76 В и 2,06 В; это **опасный
  глубокий разряд** для обычных Li-ion ячеек. Не использовать их
  в машине и не продолжать зарядку без оценки безопасности элементов.
- **Нельзя проводить физическое испытание двигателей**, пока
  не восстановлена I²C-связь, не проверены питание управляющей платы,
  общая земля и возможность физического отключения моторного питания.

### Исправление цикла переподключения G910 (25.10.2026)

В журнале обнаружено: BlueZ дважды принимал `Device1.Connect()`
(00:50:30, 00:50:49), но спустя секунды связь исчезала
(`bluetoothctl info` показывал `Connected: no`). Ранее служба принимала
успешный ответ метода за устойчивое подключение и немедленно обнуляла
счётчик ошибок. Поэтому `SCAN` мог вообще не запускаться при коротких
потерях соединения.

Исправлено в `bluetooth_autoconnect.py`:
- ответ `Connect()` теперь считается **запросом подключения**, не
  подтверждением работающего HID;
- `STATUS: ... HID services resolved` печатается только при
  `Connected=True` и `ServicesResolved=True` в новом опросе BlueZ;
- короткие соединения (менее 20 секунд) и безрезультатные запросы
  учитываются как неудачи, затем запускается BR/EDR-сканирование;
- если связь держится более 20 секунд, счётчик ошибок очищается.

Это исправление алгоритма **не доказывает**, что сам геймпад перестанет
обрывать Bluetooth. Если после обновления связь не удерживается,
следует проверить `journalctl -u bluetooth.service` и `dmesg`
для диагностики HID/состояния контроллера; не удалять сопряжение без причины.

```bash

git pull --ff-only
python3 -m py_compile src/ismartcar/controllers/bluetooth_autoconnect.py
sudo systemctl restart ismartcar-gamepad.service
sudo journalctl -u ismartcar-gamepad.service -f
```

### Пятиминутная проверка соединения G910 и процесса (25.10.2026)

**Подтверждённый аппаратный сбой:** при полностью выключенном G910
`bluetoothctl info 05:67:39:43:89:01` показывал `Connected: no`,
а `sudo hcitool -i hci1 con` — всё ещё существующую ACL-запись
`05:67:39:43:89:01`. На работающей Raspberry Pi эту зависшую запись
успешно убрала **адресная** команда:

```bash
sudo btmgmt -i hci1 disconnect -t public 05:67:39:43:89:01
```

По просьбе пользователя добавлен независимый
`gamepad_watchdog.py` и systemd-таймер с **интервалом 5 минут**.
Он находит адаптер по MAC ASUS, а не по постоянно зафиксированному `hci1`.
Каждые пять минут он:

1. Сравнивает `Connected` (BlueZ) и наличие ACL у G910 в таблице HCI.
   **Дважды с интервалом 4 секунды** подтверждает несовпадение.
   - `Connected: no`, **ACL есть**: использует адресный
     `btmgmt disconnect` (это уже проверено на оборудовании).
   - `Connected: yes`, **ACL нет**: вызывает
     `org.bluez.Device1.Disconnect()` у G910, чтобы убрать фантомное
     подключение BlueZ, после чего обычная служба повторит `Connect()`.
   - Согласованное состояние (оба подключены либо оба отключены)
     **не трогает**. Сопряжение `pair/trust` сохраняется.
2. Проверяет файл heartbeat `/run/ismartcar-gamepad.heartbeat`,
   который обновляет цикл автоподключения примерно каждые 8 секунд.
   Если цикл не работал **более 150 секунд** или служба не активна,
   вызывает `systemctl restart ismartcar-gamepad.service`.
   Это завершает старый Python-процесс штатно через systemd и запускает новый.
   Он **не перезапускает** службу при обычном выключении G910.
3. Не обращается к GPIO, PWM, моторам или сервоприводам.

### Краткий стендовый импульс тяговых моторов с G910 (25.10.2026)

В коде `g910_motor_test.py` **по умолчанию сохранён запрет**
на включение PWM при текущем `get_throttled & 0x5 != 0`.
На Raspberry Pi ранее фактически измерялось только **4,60 В на 5V GPIO**,
так что риск внезапного перезапуска реальный.

Для строго контролируемого стендового эксперимента добавлен
**явный** флаг `--accept-undervoltage`, который работает только вместе с
`--arm`. В этом режиме длительность импульса снижена с 0,7
до **0,25 секунды**, время сессии — с 90 до **25 секунд**,
а PWM ограничен 30%. Без флага остаются прежние ограничения.

**Перед тестом:** шасси надёжно закреплено, колёса вывешены, подача
питания на двигатель доступна для немедленного физического отключения.
Программная команда STOP **не может гарантироваться** при перезагрузке Pi.
Никакой аппаратный испытательный режим не оправдывает использование
аккумуляторов Li-ion, ранее разряженных до 1,76 и 2,06 В — такие
элементы требуется исключить из эксплуатации.

```bash
cd /home/pi/iSmartCar
git pull --ff-only
python3 -m py_compile src/ismartcar/controllers/g910_motor_test.py
python3 src/ismartcar/controllers/g910_motor_test.py      # просмотр, без GPIO/I2C
# Только с безопасными аккумуляторами и физическим выключателем питания двигателей:
sudo python3 src/ismartcar/controllers/g910_motor_test.py --arm --accept-undervoltage
```

Удержать левый стик вверх, кратко нажать A: не более одного импульса
на нажатие. B завершает программу. **Этот режим — сознательное временное
исключение для стендовой проверки, а не решение проблемы питания.**

### Диагностика кнопки A перед включением тяговых двигателей (25.10.2026)

По `gamepad_probe.py` подтверждены события `ABS_Y` (0 — стик вверх,
128 — центр) и `BTN_SOUTH` (1 — нажатие A, 0 — отпускание,
2 — автоповтор удерживаемой кнопки). Первый аппаратный тест
`g910_motor_test.py --arm --accept-undervoltage` показал `READY`,
но **не показал `PULSE`**; значит, команда запуска PWM
тогда не была отправлена. Это не доказательство неисправности моторов.

Добавлен **`--input-test`**, повторяющий логику распознавания
начала импульса, но **вообще не вызывающий I²C, GPIO или PWM**.
В диагностике показываются `STICK`, `BLOCKED A` и
`WOULD PULSE forward/reverse`. В моторном режиме добавлены
`BLOCKED A` и `REQUEST` для выяснения причины отсутствия `PULSE`.

Запускать при выключенном питании тяговых двигателей:

```bash
cd /home/pi/iSmartCar
git pull --ff-only
python3 -m py_compile src/ismartcar/controllers/g910_motor_test.py
sudo python3 src/ismartcar/controllers/g910_motor_test.py --input-test
```

После запуска **сначала** отклонить левый стик вверх, **затем**
нажать кнопку A и удерживать секунду. Ожидается
`WOULD PULSE forward: A=1, throttle=+100% (NO OUTPUT)`.
Нажать B для выхода. Если нажать A при нейтральном стике,
ожидается `BLOCKED A`; `BTN_SOUTH=2` никогда не
считается новой командой. В моторном режиме импульс
также запрашивается только свежим нажатием A при уже
отклонённом стике: это защищает от неожиданного запуска
при удерживаемой кнопке A и последующем движении стика.

**Важно:** на Raspberry Pi непосредственно измеряли 4,60 В;
в этом состоянии физические импульсы пока не повторять,
поскольку программный стоп при перезагрузке Pi ненадёжен.

### Прямой стендовый тест трёх сервоприводов и моторов (без G910)

Создан самостоятельный `src/ismartcar/hardware/bench_actuators_test.py`:
не использует Bluetooth, `evdev` или кнопки геймпада. Карта контактов
взята из существующего `actuator_mapping.py` и оригинального

- **CH4/CH5** — PWM левого/правого тяговых моторов (~39% мощности).

пропускает этот импульс. После каждой операции выводится FULL_OFF,

**Измеренные 4,60 В на Raspberry Pi ниже нормы**, поэтому этот

### Основная программа управления iSmartCar с G910 (25.10.2026)

**Файл:** `src/ismartcar/controllers/g910_main.py`. Используются проверенные
каналы SunFounder: PCA9685 CH0 (руль), CH14 (камера PAN),
CH15 (камера TILT), CH4/CH5 (моторы), GPIO.BOARD 11/12/13/15
(направление двигателей). Сервоприводы ограничены уже проверенными
стендовыми диапазонами:
руль 435–465, камера PAN 435–465, камера TILT 268–292,
частота 60 Гц. Управление — без отдельного GUI и без ввода команд движения
в SSH.

| G910 | Функция |
| --- | --- |
| Левый стик ←/→ | Рулевой сервопривод CH0 |
| Левый стик ↑/↓ | Вперёд/назад, регулируемая тяга CH4/CH5 |
| **Правый стик ←/→** | Горизонтальный поворот камеры CH14 |
| **Правый стик ↑/↓** | Вертикальный наклон камеры CH15 |
| A | Разрешение моторной тяги при удержании (deadman); в тестовом режиме один импульс за нажатие |
| B | Аварийная остановка и выход |
| X | Центрирование рулевого сервопривода |
| Y | Центрирование двух сервоприводов камеры |

Без параметра `--arm` **только просмотр событий**, без I²C/GPIO.
Файл `g910_drive.py` и успешно выполненный стендовый тест не
изменены. `g910_main.py` работает отдельно и не устанавливается как
systemd-сервис автоматически.

```bash

python3 -m unittest discover -s tests -p 'test_g910_main.py' -v

```

В режиме просмотра перемещать оба стика — будут появляться строки
`SERVO CH0`, `SERVO CH14`, `SERVO CH15`. При удержании A
и отклонении левого стика появится `WOULD PULSE`, но моторы выключены.

**Первое реальное испытание только сервоприводов**, с закреплённой
машинкой и свободным ходом механизмов:

```bash

```

**Одновременное испытание сервоприводов и коротких тяговых импульсов**
только с вывешенными колёсами, исправными аккумуляторами и физическим
отключением питания моторов:

```bash

```

Реальная непрерывная пропорциональная тяга предусмотрена в
`--arm --drive --hardware-cutoff-confirmed`, однако **заблокирована
при активном `get_throttled & 0x5`**. Этот режим следует использовать
только после восстановления питания Raspberry Pi, установки и испытания
независимого аппаратного выключателя/сторожа питания тяговых моторов.
Флаг `--accept-undervoltage` с `--drive` несовместим.

Сейчас на Raspberry Pi фактически измерено **4,60 В** и
`get_throttled=0x50005`; непрерывное движение при таком питании
опасно, потому что перезагрузка Pi может оставить выходы двигателя
активными. Клавиша B и программный таймаут — не аппаратный стоп.
Это первая сборка основного контроллера: аппаратная проверка
`g910_main.py` ещё не проводилась, хотя отдельные три сервопривода
и моторы обоих направлений успешно протестированы.

### Инцидент при первом запуске g910_main.py (25.10.2026)

После запуска `--arm --servos-only --accept-undervoltage` было
`PCA9685: ... SLEEP=True`, затем SSH оборвался с
`client_loop: send disconnect: Broken pipe`. Пользователь наблюдал
сильный поворот камеры вправо и наклон вниз, зависание управления и
отключение G910; питание пришлось отключить физически. Не считайте
этот аппаратный тест успешным.

**Вероятная причина в старой версии main:** непосредственно после
`set_frequency(60)` программа автоматически включала CH0, CH14 и
CH15 в положения 450, 450 и 280 и **оставляла их непрерывно
энергизированными**. В успешном `bench_actuators_test.py`
каждый сервопривод включался по очереди кратковременно, затем
его PWM отключался. Одновременное длительное удержание могло
создать нагрузку на механику/питание. Сам `Broken pipe`
не доказывает перезагрузку Raspberry Pi, только обрыв SSH.

**Исправление:** удалены все автоматические сервокоманды при
запуске. Введены очередь команд по стикам и **только один активный
серво-канал за раз**; после 0,18 с PWM соответствующего канала
выключается. Моторные импульсы с этим временем не пересекаются.
Текущие центры не считаются откалиброванными! Застрявшие или
нагревающиеся приводы должны быть обесточены до разборки механики.

Безопасная проверка на Raspberry Pi после физического отключения
питания **сервоприводов и моторов**:

```bash
cd /home/pi/iSmartCar
git pull --ff-only
python3 -m py_compile src/ismartcar/controllers/g910_main.py
sudo python3 src/ismartcar/controllers/g910_main.py
```

Режим по умолчанию не пишет GPIO/I²C. Чтобы выяснить,
перезагружалась ли Pi при аварии, после переподключения проверить
`uptime -s` и `journalctl -b -1 -n 30 --no-pager`
(если предыдущая загрузка сохранена в journal).

Пока пользователь не подтвердит стабильность новой программы,
**не запускать** режимы `--arm` и `--drive` и не подключать
полную механическую нагрузку. Измеренные ранее 4,60 В на Pi
остаются фактической проблемой питания. Поддержка аварийной остановки
по Bluetooth не заменяет независимый аппаратный разрыв питания
выходов PWM (например, через аппаратную линию OE PCA9685).
